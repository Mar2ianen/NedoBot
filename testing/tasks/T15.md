# T15 — Coverage-guided fuzz: parser, entities and QR

**Репозиторий:** teloxide-antispam + NedoBot. **Зависимость:** T14. **Тип:** implementation + actual tests, не просто план.

**Перед стартом:** прочитать актуальный `AGENTS.md` и соответствующий production/test код, `testing/references/INVARIANTS.md`, `testing/references/VALIDITY_LEVELS.md`, `testing/references/CORPUS_PRIVACY.md`. Начинать от свежего `main`, не использовать старые PR head. Работать офлайн на синтетике и тестовых БД.

## Implementation
- Set up `cargo-fuzz` targets using isolated fuzz workspaces following current Rust Fuzz Book: raw URL parse, structured Telegram link/entity adapter, QR payload handling and decoded-image boundary (bounded).
- Distinguish V1/V2 structured `Arbitrary` targets from V3 raw-byte robustness targets; don't claim raw byte fuzz as Bot API-valid.
- Use static synthetic seed files only; tools `cargo fuzz tmin` and `cmin` for minimizing failures and corpora. Respect OSS crate feature matrix.
## Properties
- No panic, excessive allocation or infinite work on V3; semantic equivalence asserted by an independent oracle for structured cases.
- Accept rate for structured cases high; raw V3 bugs tracked as robustness, not Telegram semantics. No private seeds/corpus artifacts uploaded.
## Acceptance
- Target run commands and fixed time budgets documented; one synthetic intentionally introduced defect detected and minimized, then repaired.
- CI/nightly coverage logs contain target counts, seeds, toolchain and artifact privacy checks; use nightly/LLVM toolchain only where needed.

## Общая проверка и сдача

1. Новый тест должен **сначала** воспроизвести ошибку или доказать ожидаемый инвариант; expected behavior не брать из проверяемой функции.
2. Оформить V1/V2/V3 для новых входов, оценить генерацию/отказы, сохранить воспроизводимый seed или минимальный trace.
3. Выполнить применимые `cargo fmt`, `cargo test`, `cargo check`, Clippy, feature matrix и интеграции с **ненулевым** числом тестов; для изменённых исполняемых путей показать доказательство из CI.
4. Не делать production deploy, Telegram API actions, изменения enforcement и работу с закрытым корпусом без доступа. Никаких сырых приватных данных в diff/логах/артефактах.
5. Написать `T15` completion report по `testing/references/TASK_REPORT_TEMPLATE.md`: точный SHA, PR, tests/CI, инварианты, баги, privacy, ограничения. Только после его завершения переходить к следующему T.
