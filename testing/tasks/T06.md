# T06 — Full Bot API Update lifecycle and handler integration

**Репозиторий:** NedoBot. **Зависимость:** T05. **Тип:** implementation + actual tests, не просто план.

**Перед стартом:** прочитать актуальный `AGENTS.md` и соответствующий production/test код, `testing/references/INVARIANTS.md`, `testing/references/VALIDITY_LEVELS.md`, `testing/references/CORPUS_PRIVACY.md`. Начинать от свежего `main`, не использовать старые PR head. Работать офлайн на синтетике и тестовых БД.

## Cases
- Schema-valid `Update`: `message`, `edited_message`, `channel_post`, `edited_channel_post`, inaccessible/reply wrappers as supported by pinned teloxide; text, caption, media, inline keyboard, service messages.
- Strict required and cross-field constraints; synthetic values annotated V2 unless Bot API-realizable is verified. Test unsupported or unknown Update types as compatibility checks, not fabricated Telegram behavior.
## Properties
- Duplicate update idempotent; edited content consistently supersedes old derived URL/QR state.
- Adapter-to-handler-to-DB path handles valid full structs with correct user/chat attribution and correct no-op behavior for irrelevant event type.
- Weird user input never gets interpreted as internal SQL, HTML, prompt instructions, or network fetch.
## Acceptance
- One full path integration with disposable PG and mock transport (no Telegram API). Actor IDs and updated message ID verified.
- Robustness lane separate from documented-valid lane, no silently ignored unsupported update events.

## Общая проверка и сдача

1. Новый тест должен **сначала** воспроизвести ошибку или доказать ожидаемый инвариант; expected behavior не брать из проверяемой функции.
2. Оформить V1/V2/V3 для новых входов, оценить генерацию/отказы, сохранить воспроизводимый seed или минимальный trace.
3. Выполнить применимые `cargo fmt`, `cargo test`, `cargo check`, Clippy, feature matrix и интеграции с **ненулевым** числом тестов; для изменённых исполняемых путей показать доказательство из CI.
4. Не делать production deploy, Telegram API actions, изменения enforcement и работу с закрытым корпусом без доступа. Никаких сырых приватных данных в diff/логах/артефактах.
5. Написать `T06` completion report по `testing/references/TASK_REPORT_TEMPLATE.md`: точный SHA, PR, tests/CI, инварианты, баги, privacy, ограничения. Только после его завершения переходить к следующему T.
