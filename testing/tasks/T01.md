# T01 — Deterministic harness, replay and reproducibility

**Репозиторий:** NedoBot + teloxide-antispam. **Зависимость:** —. **Тип:** implementation + actual tests, не просто план.

**Перед стартом:** прочитать актуальный `AGENTS.md` и соответствующий production/test код, `testing/references/INVARIANTS.md`, `testing/references/VALIDITY_LEVELS.md`, `testing/references/CORPUS_PRIVACY.md`. Начинать от свежего `main`, не использовать старые PR head. Работать офлайн на синтетике и тестовых БД.

## Implementation
- Audit current test runners, features and `AGENTS.md`; map test boundaries by crate. Introduce documented `testing` harness modules, not a new runtime dependency for the bot.
- Add `proptest` in test/dev contexts, generator strategy builders that return reproducible seeds, and short/long run settings. Do not rely on an invented arbitrary RNG seed API: verify the installed proptest version and its runner settings.
- Add a replay command or executable test invocation for one failing synthetic seed and one minimal operation trace; emit only sanitized test metadata.
- Add shared `CaseReport`, validity class, origin, and invariant identifier schema. Keep full cases outside standard logs by default.
- Establish fast tests with meaningful structured valid case ratios; write down rejected generations and reasons.
## Acceptance
- A deliberately broken local fixture fails, is reduced and replays identically in two consecutive invocations; fix it without changing runtime behavior.
- One synthetic corpus read test and one proptest property run with **nonzero** test counts in CI; separate slow lane documented.
- Existing feature matrix/CI green; no tracked private corpora or secrets.

## Общая проверка и сдача

1. Новый тест должен **сначала** воспроизвести ошибку или доказать ожидаемый инвариант; expected behavior не брать из проверяемой функции.
2. Оформить V1/V2/V3 для новых входов, оценить генерацию/отказы, сохранить воспроизводимый seed или минимальный trace.
3. Выполнить применимые `cargo fmt`, `cargo test`, `cargo check`, Clippy, feature matrix и интеграции с **ненулевым** числом тестов; для изменённых исполняемых путей показать доказательство из CI.
4. Не делать production deploy, Telegram API actions, изменения enforcement и работу с закрытым корпусом без доступа. Никаких сырых приватных данных в diff/логах/артефактах.
5. Написать `T01` completion report по `testing/references/TASK_REPORT_TEMPLATE.md`: точный SHA, PR, tests/CI, инварианты, баги, privacy, ограничения. Только после его завершения переходить к следующему T.
