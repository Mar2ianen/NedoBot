# T11 — PostgreSQL advisory locks, cancellation and deadlocks

**Репозиторий:** NedoBot. **Зависимость:** T10. **Тип:** implementation + actual tests, не просто план.

**Перед стартом:** прочитать актуальный `AGENTS.md` и соответствующий production/test код, `testing/references/INVARIANTS.md`, `testing/references/VALIDITY_LEVELS.md`, `testing/references/CORPUS_PRIVACY.md`. Начинать от свежего `main`, не использовать старые PR head. Работать офлайн на синтетике и тестовых БД.

## Interleavings
- Same user profile vs edit vs QR refresh, two different users, cancel while waiting for lock, cancel while holding lock, pool contention, task panic and close-on-drop, error after PG lock obtained.
- Validate lock namespacing by instance/chat/user; inspect collisions and interactions with other job/audit locks for deadlock order.
## Properties
- Same target writes serial, different users can progress, no stale shadow overwrite. Canceled lock connection isn't reused with held session advisory lock.
- Lock-acquiring helper always releases on success/error/cancel. Pool exhaustion doesn't deadlock when operation needs additional connection.
## Acceptance
- Use barriers/Notify and deterministic scheduling, not only sleeps; test with pool sizes 1/2/5 explicitly where supported and define safe minimum.
- CI logs prove nonzero PG tests; documented worst-case lock and latency budget.
