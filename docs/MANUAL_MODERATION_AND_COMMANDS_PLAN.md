# Ручная модерация и архитектура команд

Статус: MVP реализован в отдельной feature `manual-moderation`; в Недоботе она не включена, runtime-флаги выключены. В прод не выкатывалось. Ниже зафиксированы реализованные правила и оставшиеся этапы общего переноса команд.

## Цели

1. Добавить админские `/mute`, `/ban`, `/warn` с необязательной причиной, понятным сроком и записью в журнал.
2. Добавить обратные/просмотровые команды, пакетную модерацию и `/undo`.
3. Разделить Telegram-командный frontend и общий backend модерации. Будущая автоматическая антиспам-модерация должна вызывать тот же backend, а не дублировать Telegram API и бизнес-правила.
4. Показывать действующие меры в существующем `/userstats` (`/userstatus`).
5. Постепенно разнести все существующие команды по такому же принципу, сохранив их поведение.
6. Оставить ручной frontend выключенным для Недобота.

## Что есть сейчас

- `src/main.rs` регистрирует один `filter_command::<Command>()` и передаёт его в `telegram::command_handler::handle_command`; новые ручные команды маршрутизируются этим handler только при compile/runtime gate.
- Имена и грамматика статических команд собраны в `src/telegram/commands.rs`; новый frontend вынесен в `src/telegram/manual_moderation.rs`, данные и PostgreSQL lifecycle — в `features::manual_moderation`.
- Отчёты, статистика, память, голосовые, `/ask` и аудит новых участников уже имеют feature-модули, но Telegram-адаптер и маршрутизация всё ещё частично сосредоточены в общем обработчике.
- `features::stats` уже собирает `/userstats` из typed report data и Telegram member snapshot; оба HTML/rich-renderer используют общий DTO. Snapshot показывает наблюдаемый Telegram status, но не причину, автора и срок именно наших наказаний.
- Cargo-флаг `moderation` уже входит в `default`; он включает аудит новых участников, spam review и `/report`. Использовать его для новых ручных действий нельзя: это включило бы слишком широкий контур в Недоботе.

## Предлагаемые границы

```text
Telegram updates
      │
      ▼
Telegram command frontend ── parse targets/reason/duration, obtain actor context, render result
      │
      ▼
Moderation application service ── policy/idempotency/audit/undo ── Telegram action port
      ▲                                                                  │
      │                                                                  ▼
Anti-spam decision frontend (later)                              Postgres repository
      │                                                                  ▲
      └──────── same typed use cases ────────────────────────────────────┘

`/userstats` ── stats service ── ModerationSummary read model ── HTML/rich renderer
```

### Backend

Реализованный backend `features::manual_moderation` отделяет типы и PostgreSQL lifecycle от Telegram command frontend. Он принимает primitive/typed данные (chat, target, actor, action, expiry и необязательную причину), а не `teloxide::Message`:

- `chat_id`, `target_user_id`, `actor_user_id` (для автоматического решения actor отсутствует); один batch содержит один или несколько targets;
- действие и длительность;
- необязательная причина;
- источник (`manual_command`, позднее `anti_spam`), ссылка на исходное сообщение/решение и idempotency key;
- для автоматических решений — структурированные evidence/signals, не произвольный SQL.

Repo/backend владеет сохранением intent, статусов, предупреждений, supersession, undo и аудита. Telegram frontend выполняет actor/target preflight и typed Telegram API-вызовы. Будущий anti-spam должен вызывать backend use-case/repository path и использовать тот же ledger; ему не следует писать в таблицы вручную или обходить lifecycle. Отдельную transport-neutral executor abstraction для автоматических side effects добавить перед включением автоматических наказаний.

Telegram adapter реализует typed-порт через методы teloxide fork-а. Не собирать Bot API HTTP URL или собственные wire-типы. Неудача/неопределённый результат Telegram API не должен записываться как успешное наказание.

### Frontend команд

Командный frontend превращает сообщение или reply в типизированную batch-команду, передаёт actor/capabilities backend-у и рендерит результат по каждому target. Frontend не содержит SQL, расчёта сроков, решения «кого наказывать» или вызовов LLM. Для `/help` и меню используется единый каталог команд с метаданными: имя, описание, feature, scope, права, синтаксис.

## Команды и семантика

Синтаксис ниже — предлагаемый интерфейс. Поддержать как ответ на сообщение, так и явный Telegram ID; `@username` разрешать только по однозначной записи, уже известной боту. Bot API не предоставляет надёжного общего поиска участника по username. Если цель не разрешилась однозначно — попросить ответить на её сообщение или передать ID.

| Команда | Предлагаемое поведение |
|---|---|
| `/mute [срок=1d] [цели...] [-- причина]` | Временно запретить писать. Причина необязательна. |
| `/ban [срок=навсегда] [цели...] [-- причина]` | Исключить из чата. Пропущенный срок означает постоянный бан; причина необязательна. |
| `/warn [срок=30d] [цели...] [-- причина]` | Записать отдельное предупреждение; три активных warn автоматически приводят к mute на 5 дней. |
| `/unmute [цель] [-- причина]` | Снять только известный боту mute, восстановив chat default permissions; причина необязательна. |
| `/unban [цель] [-- причина]` | Снять известный боту ban; команда сама не добавляет участника обратно; причина необязательна. |
| `/unwarn [цель] [#id\|all] [-- причина]` | Отозвать одно или все активные предупреждения; причина отзыва необязательна. |
| `/warns [цель]` | Показать активные/истёкшие предупреждения и причины модераторам. |
| `/modlog [цель] [limit]` | Показать последние действия по пользователю или чату с актором, временем, причиной и статусом. |
| `/undo` | Компенсировать последнюю batch-команду этого администратора в этом чате, где хотя бы один target был успешно обработан; результат показывается отдельно по каждому target. |
| `/kick [цель] -- <причина>` | Отдельный следующий шаг: удалить участника с возможностью вернуться. Не смешивать с постоянным баном. |
| `/purge_user` | Отдельный следующий шаг: удаление недавних сообщений требует отдельной явной команды и права `can_delete_messages`; не запускать как побочный эффект mute/ban. |

Примеры для MVP:

```text
(reply) /mute -- флуд                 # mute на 1 день по умолчанию
/mute 2d3h @alice @bob -- повторная реклама
(reply) /ban -- фишинг                 # постоянный бан по умолчанию
/ban 7d @alice @bob -- мошенническая ссылка
(reply) /warn -- повторный оффтоп      # срок warn задаёт конфиг
/warns @username
/unmute @username -- ограничение больше не требуется
/undo
```

Правила парсинга:

- Срок — распознаваемый отдельный токен с поддержкой `30m`, `2h`, `3d`, `2d3h`; ноль, отрицательные значения, переполнение и неизвестные единицы отклоняются. Для `/mute` default `1d`, для `/ban` default forever, для `/warn` — явно заданный конфигурацией TTL (предлагается `30d`).
- `--` отделяет необязательный reason от списка targets/duration. Если разделитель отсутствует или текст после него пуст, действие выполняется без причины. Для `/undo` отдельный reason не принимается.
- Разрешены несколько targets в одном сообщении, до 20 на batch в MVP. Источником может быть reply и/или явные ID/однозначно известные username; reply добавляется к списку, одинаковые ID дедуплицируются. Если хотя бы один target не разрешён однозначно, недопустим или не может быть проверен, весь batch отклоняется до первого side effect.
- Синтаксическая/проверочная атомарность не обещает атомарности Telegram API: после успешного preflight действия исполняются по одному. Успех, отказ и неопределённый outcome фиксируются отдельно на каждую цель; частичный успех явно показывается и не маскируется общим «готово».
- Успешная новая команда `/mute` или `/ban` заменяет только прежнее активное mute/ban для того же пользователя и чата. Неуспешная или неопределённая команда не вытесняет прежнюю меру. `/warn` создаёт отдельную накопительную запись; mute/ban не очищает предупреждения. `/mute` для уже забаненного участника не снимает бан автоматически — операция отклоняется с подсказкой `/unban`, затем повторить после возвращения участника.
- `/undo` находит последнюю применённую команду этого администратора в текущем чате. Он снимает mute/ban или восстанавливает предыдущую ещё актуальную меру; warn отзывает/восстанавливает с append-only событиями. Перед исполнением повторно проверяются все targets; неизвестный исход и конкурентное действие fail closed.
- Конечные сроки ограничены 30 секундами…365 днями. Постоянный ban реализуется без `until_date`; `/mute` по умолчанию сутки. Warn по умолчанию действует 30 дней и может получить срок явно; после трёх активных warn назначается отдельный mute на пять дней. У истечения не нужен worker.

### Edge cases: контракт отказа и частичного выполнения

| Ситуация | Обязательное поведение |
|---|---|
| В batch один target неизвестен, неоднозначен, является администратором или не проходит preflight | Отклонить весь batch до первого Telegram side effect; вернуть конкретные ошибки, не менять валидные цели отдельно. |
| Дубликат target в reply и в списке | Выполнить действие один раз по Telegram user ID; в ответе показать дедупликацию, не создавать второй warn. |
| Telegram отказал на части целей или бот потерял права уже после preflight | Зафиксировать исход отдельно по каждому target, остальные безопасные цели обработать, показать частичный результат; не помечать отказавший target активным. |
| Update продублирован, команда пришла повторно после сетевого timeout | Вернуть сохранённый batch/result по idempotency key. Для `unknown` сначала reconciliation; не слать повторное наказание вслепую. |
| Username не известен боту, был изменён/переиспользован или разрешается в несколько записей | Отказать до применения и запросить reply либо numeric ID; не предполагать, что username — постоянный идентификатор. |
| Target уже забанен, запрошен `/mute` | Не делать implicit unban/rejoin; отказать только этому действию до исполнения с явной подсказкой. |
| В Telegram есть мера, которой нет в локальном журнале | Не считать её своей и не обещать безопасный `/undo`; при конфликте отказать или пропустить target и указать, что источник неизвестен. |
| Два админа одновременно выдают меры одному target | Сериализовать/сверять состояние по `(chat_id, target_user_id)`; последняя подтверждённая Telegram мера становится current, каждый результат аудируется. Не скрывать проигравший конфликт как успех. |
| `/undo` затрагивает batch с несколькими целями, но после него один target уже модерирован другим админом | Компенсировать только свои подтверждённые действия, которые всё ещё current; конфликтный target пропустить, остальные обработать, итог показать по каждому. |
| `/undo` вызван после естественного истечения временной меры | Не снимать новую/внешнюю меру и не возрождать superseded наказание автоматически; отметить target как уже истёкший/no-op. |
| Бот не может получить актуальные права/статус или actor anonymous | Fail closed для авторизации; не полагаться на старый snapshot как на подтверждение admin rights. |
| Команда пришла не в managed group, в отредактированном сообщении или не как Telegram command entity | Не исполнять; приватный чат, чужой chat scope и произвольное упоминание текста `/ban` не должны обходить routing policy. |

Ban разрешается по numeric ID или известной chat-записи даже если участник уже вышел; mute и warn требуют подтверждённого текущего участника. Если статус участника установить нельзя, preflight отказывает. Это оставляет возможность запретить повторный вход известному ушедшему пользователю, но не позволяет выдавать предупреждения или mute «вслепую».

Документация ChatKeeperBot служит ориентиром для reply/target и составных сроков, временных и постоянных мер, kick и warn. Default `/mute=1d`, несколько целей, замена активной меры, необязательная причина, порог 3 warn → mute 5d и `/undo` — требования именно этого проекта. Shieldy — ориентир по автоматическому антиспам-контуру, а не источник синтаксиса ручных команд.

## Статусы пользователя и `/userstats`

Расширить существующий путь, а не создавать вторую команду статусов:

- `stats::service::user_stats_report_data` получает типизированный `ModerationSummary` из moderation read-model для пары `(chat_id, user_id)` и добавляет его в существующий `UserStatsReportData`.
- Имеющиеся `render_html::user_stats` и `render_rich::user_stats` отображают одинаковые поля: активный mute/ban и expiry (или «навсегда»), активное число warn. Причины доступны в admin-only журнале, не в общей карточке.
- `/userstats` сохраняет существующие правила доступа и способ доставки ответа. Он показывает сводку мер без внутренних технических данных; причины показывать только тем, у кого по ACL есть доступ к модерации, если сам `/userstats` доступен шире. Actor и полная история остаются в admin-only `/modlog`; полный журнал не отправлять в общий чат.
- Telegram member snapshot остаётся источником наблюдаемого membership (`member/admin/restricted/left/banned`), а moderation records — источником наших причин и сроков. Если Telegram показывает `restricted`/`banned`, но соответствующего локального действия нет, показать «статус Telegram; источник/причина неизвестны», не придумывать причину и не создавать задним числом наше действие.
- Read-model не должен блокировать команду сетевым вызовом Telegram: если moderation-хранилище недоступно, показать текущие доступные данные и пометить сведения о мерах как временно недоступные, не отображая устаревший summary как достоверный.

Нужно отдельно проверить фактическую регистрацию `/userstatus` и поведение видимости ответа в текущем коде при реализации; архитектурный путь `/userstats` и два renderer уже существуют.

## Авторизация и защита

- На каждый ручной вызов повторно получать/проверять членство актора через `getChatMember`; при ошибке Telegram — fail closed. Кэш можно добавить позже с коротким TTL и обязательной инвалидацией, но не использовать как единственный источник права.
- Администраторское право проверяется в чате вызова. Список reviewer-ов spam review не даёт права на `/ban` автоматически.
- Проверять право самого бота отдельно для операции: `can_restrict_members` для mute/ban/unmute/unban; `can_delete_messages` для удаления чужого сообщения в супергруппе. Админ пользователя и админ-бот — две разные проверки.
- Защищать creator/admin, самого бота, анонимные `sender_chat` и неизвестные/внешние чаты. На админскую цель модерация не применяется даже если вызывающий админ, пока не будет отдельного явного owner policy.
- Команда и target должны относиться к одному managed chat. Глобальная модерация по всем чатам не входит в MVP.
- Причина и пользовательские поля считаются недоверенными данными; при HTML-рендере обязательны существующие `telegram::html` helpers. Токены, полный raw update и чувствительные данные в лог не писать.
- Отдельно хранить классификационную метку spam и факт санкции: warn/ban не должны автоматически добавлять `spam_label_events`. Спам-разметка — отдельное явное решение/источник.
- Проверка актора и каждого target делается в контексте chat_id команды; неизвестный статус, ошибка Telegram или невозможность отличить анонимный `sender_chat` от пользователя означает отказ до исполнения.
- При batch preflight нельзя допускать частичную проверку перед применением: сначала полностью разобрать команду, дедуплицировать targets, разрешить их, проверить запреты и bot capabilities для каждого, затем только создавать исполняемые requests.
- События Telegram и повторная доставка update могут приходить повторно/не по порядку. Command update имеет уникальный idempotency key; observed member update не создаёт локальное наказание и не перезаписывает его audit history.
- Внешняя/ручная санкция, видимая только как Telegram `restricted`/`banned`, не должна автоматически «усыновляться» локальным журналом. `/unmute`, `/unban` и `/undo` обязаны сообщать, если исходную меру бот не знает и безопасно восстановить состояние нельзя.

## Данные и выполнение

Предлагается additive migration с раздельными моделями:

1. `manual_moderation_batches` — запись команды с `chat_id`, `actor_user_id`, message-id idempotency key и command kind.
2. `manual_moderation_actions` — действие на target с nullable reason, сроком, execution status и связью `supersedes_action_id`.
3. `manual_moderation_events` — append-only журнал переходов (`requested`, `applied`, `failed`, `unknown`, `revoked`, `superseded`, `undo_skipped`) с actor, временем и безопасными деталями.
4. `manual_moderation_operations` — durable intent для внешнего Telegram side effect (`apply`, `revoke`, `undo`, `restore`) со статусами `pending`, `processing`, `succeeded`, `failed`, `unknown` и lease. Состояние ограничения остаётся в `manual_moderation_actions`; запуск и неопределённый исход API-вызова фиксируются отдельно.

Правила уникальности/конкурентности:

- Уникальный idempotency key на incoming command предотвращает повторное применение при повторной доставке одного update. Каждая цель также имеет уникальную пару `(batch_id, target_user_id)` после дедупликации.
- На одного пользователя/чат может быть не более одной текущей активной меры из семейства mute/ban; warn — отдельные многократные записи. Успешное новое mute/ban атомарно помечает предыдущую меру superseded, но только после подтверждённого успеха новой меры. Неуспех или ambiguous outcome не вытесняет текущую меру. Прежнюю меру можно восстановить через `/undo`, только если её собственный срок ещё не истёк.
- Перед Telegram side effect фиксировать intent и lease/processing статус. Если процесс падает после запроса Telegram, но до записи ответа, outcome считается `unknown`: reconciliation через typed `getChatMember` может подтвердить наблюдаемое ограничение, но не должна приписывать его боту без достаточной связи; опасный автоматический повтор не делать.
- Для batch сначала в одной транзакции записать все operation intents как `pending`, затем переводить каждую цель в `processing` непосредственно перед её Telegram-вызовом. Lease истёкшего `processing` переводит intent и связанную action в `unknown`; `pending` не становится `unknown` от одного лишь падения процесса.
- Повтор существующего batch сначала восстанавливает истёкшие operation leases, затем делает Telegram preflight. Наблюдаемое состояние, связанное с uncertain intent этой же команды, не трактуется как внешняя мера; target остаётся `unknown` и не повторяется вслепую.
- `/undo` не переводит прежнюю superseded action в `pending` перед Telegram-вызовом: прежняя мера остаётся superseded до подтверждённого restore, после чего атомарно возвращается в `applied`. Это сохраняет unique constraints и не показывает неподтверждённую меру как активную.
- Для `/undo` использовать compare-and-set по текущей active-action/generation для каждого target. Более поздняя команда или мера неизвестного источника — конфликт: target пропустить и показать причину. Undo сохраняется отдельной batch и не стирает прежние события.
- Сразу выполнить полную валидацию всех targets перед созданием side effects; далее Telegram не даёт транзакции на batch, поэтому per-target outcomes и частичный результат обязательны. Повтор `/undo` не должен повторно отменять или восстанавливать меру.
- Telegram ban/restrict истекает через `until_date`; warn активен пока не истёк TTL и не отозван. Фоновый worker для истечения не нужен; если понадобится retry/outbox, у него должны быть bounded retry, lease и terminal failure.

`manual_moderation_*` не заменяют `spam_label_events`, `spam_review_requests` или Telegram member state. Снимок Telegram — наблюдение состояния, а не доказательство авторства успешного действия; переданная причина и результат остаются привязаны к локальному audit event.

## Feature gates и Недобот

Не переиспользовать существующий Cargo feature `moderation`: он включён в default и нужен уже работающему аудиту новых участников.

Реализованная отдельная compile-time feature `manual-moderation` отсутствует в `[features].default`. Она включает ручной frontend и backend-модуль, не меняя существующую `moderation` feature.

Плюс runtime gate на уровне сообщества и каждого чата:

```toml
[manual_moderation]
enabled = false

[chats.general]
manual_moderation = false
```

Правило запуска: runtime `enabled=true` без скомпилированной Cargo feature — startup error; feature в бинарнике при выключенном runtime/chat-флаге — нет регистрации фоновых задач и нет ответа/действия в чате. Для Недобота сохранить `manual-moderation` вне default и оба runtime-флага `false`. Существующие `/report`, new-user audit и spam-review не отключать этим новым флагом.

## Постепенное разделение всех команд

Не переписывать весь `command_handler.rs` одним большим PR. План поведения-сохраняющего переноса:

1. **Инвентаризация и characterization tests.** Зафиксировать parse, scope, admin checks, обработку reply и текст результата для каждой текущей команды; ничего не менять в поведении.
2. **Общий command catalog/router.** Описать команды, aliases, compile/runtime gate и policy в typed registry. `help` и, если потребуется, BotCommand menu строятся из одного каталога. Скрытая команда всё равно должна быть защищена на backend-уровне: меню не является ACL.
3. **Тонкий Telegram frontend.** Вынести parsing/context/rendering/permissions в транспортный слой; `main.rs` остаётся wiring. Существующие feature service/repo продолжают владеть бизнес-логикой.
4. **Миграция по feature-слайсам.** Переносить `/stats_*`, `/top*`, `/userstats`, `/report`, `/memory`, `/transcribe`, `/ask`, `/chat_note`, `/user_note` по одному набору, сохраняя команды и ответы; после каждого среза — регрессионные тесты.
5. **Новый moderation backend + manual frontend.** Реализовать parser, полный batch preflight, `/mute`, `/ban`, `/warn`, reversals, `/undo`, журнал и права с отдельным feature gate; подключить typed summary к `/userstats`.
6. **Автоматический антиспам позже.** Его policy вызывает backend use case напрямую и передаёт источник/evidence/idempotency key; ручной frontend остаётся отдельным и по-прежнему выключаемым.

Перенос команды считается законченным, когда command handler только преобразует Telegram input/output и делегирует typed use case; SQL, policy и композиция бизнес-операций находятся в feature/backend слоях. Модульное разделение само по себе не должно менять доступность, формат или побочные эффекты существующих команд.

## Тесты и критерии готовности

- Parser: defaults `/mute=1d`, `/ban=permanent`, `/warn=30d`; compound duration, границы/overflow, optional reason, аргументы цели, reply + explicit targets, username ambiguity, ID, дедупликация, лимит batch, пустые/лишние аргументы.
- Preflight/service: один недопустимый/неразрешённый target отклоняет весь batch без вызова Telegram port; actor не admin, bot capability отсутствует, target admin/bot/owner, anonymous sender, cross-chat, уже забаненный target для mute, неизвестная внешняя санкция.
- Lifecycle: новое успешное mute заменяет старое mute; успешный ban supersede-ит активный mute; mute для уже забаненного target отклоняется без auto-unban; failed/unknown новой операции не supersede прежнее; три активных warn дают mute на пять дней; TTL/revoke не портят историю.
- Batch/undo: 2+ targets, duplicate targets, один частичный Telegram failure, повтор update, два конкурирующих модератора, `/undo` после batch, повторный `/undo`, более новое действие по одному target (его пропустить), восстановление предыдущей меры/невозможность восстановления, undo предупреждений.
- PostgreSQL integration: миграции, append-only events, chat scoping, command idempotency, unique target per batch, максимум одна active mute/ban, конкурентная supersession, active warning set, CAS-конфликт undo и recovery после состояния `unknown`.
- Frontend integration: reply/ID/known username дают ожидаемые targets; запрет обычному участнику; выключенный compile/runtime/chat gate не вызывает Telegram port; ответы явно показывают partial/unknown/failure outcomes.
- `/userstats` regression: оба renderer показывают один и тот же active sanction, срок/навсегда, причину и предупреждения; неизвестный Telegram restriction не получает выдуманную причину; отсутствие локальной записи и ошибка read-model отображаются честно.
- Regression: все существующие `/help`, `/report`, статистические команды, `/ask`, notes и `/transcribe` сохраняют parsing, authorization, rendering и текущую feature gating.
- Build matrix: default Nedobot build не содержит новых ручных команд; отдельный build с `manual-moderation` проходит `cargo check/test`; включённый в config feature при отсутствующем cargo feature падает при startup.
- Для DB/policy/config изменений: `cargo fmt`, `cargo test --all-targets`, `cargo clippy --all-targets -- -D warnings` и PostgreSQL migration tests. Для реального включения — отдельный Telegram smoke только на тестовом чате, не в Недоботе.
