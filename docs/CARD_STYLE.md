# Обязательный стиль карточек NedoBot

Этот документ — обязательный контракт для новых карточек и изменений существующего вывода. Перед правкой renderer, команды или карточки модерации нужно прочитать его и выбрать соответствующий образец ниже. Правила действуют для Rich, HTML и текстового fallback.

Цель: **НедоBot не должен быть громче людей.** Карточка быстро отвечает на запрос: кто, что произошло, сколько и что можно сделать. Оформление помогает прочитать данные с телефона.

Контракт распространяется на статистику, профили, топы, репорты и ревью спама. Для структурированных ответов `/ask` обязательны те же правила ссылок, экранирования, источников и доставки; свободный ответ агента не требуется превращать в таблицу профиля.

## 1. Образцы в проекте

| Вид карточки | Образец | Обязательная структура |
|---|---|---|
| `/userstats`, `/userstatus` | [`render_rich::user_stats`](../src/features/stats/render_rich.rs), [`render_html::user_stats`](../src/features/stats/render_html.rs) | Имя пользователя, основные сведения и активность; второстепенные данные отдельно |
| `/topword` | `top_word` в тех же renderer | Только ранжированный список: место, кликабельное имя, число вхождений |
| `/topmsg`, `/bottommsg` | `ranked_users` в Rich renderer | Краткое название рейтинга, основная таблица; дополнительные показатели свёрнуты |
| `/topreact` | `top_reacted` в Rich renderer | Рейтинг с автором, числом реакций и ссылкой на сообщение; превью отдельно |
| `/stats_day`, `/stats_week`, `/stats_month` | `chat_stats` в Rich renderer | Название и период; сводка, активность и участники; подробности отдельно |
| Репорт администраторам | [`reports/render.rs`](../src/features/reports/render.rs) | Тип события, источник, цель и репортёр, причина и цитата, сведения для решения, кнопки |
| Ревью спама | [`spam_review.rs`](../src/features/spam_review.rs) | Проверяемый пользователь, риск и основания, явные кнопки подтверждения и отклонения |

Образец задаёт структуру, а не разрешает копировать весь renderer. Существующие ручные форматы дат, дублирующие подписи или случайные особенности старого вывода не становятся правилом для новых карточек. При конфликте приоритет у этого контракта.

## 2. Иерархия и плотность

- У сложной карточки допускается один основной заголовок: имя человека, вид события или название отчёта с периодом. Он должен помогать определить предмет карточки.
- Не добавлять вводные «Вот ваша статистика», «Результаты выполнения команды», повтор команды, декоративные подзаголовки и обязательный footer. Существующий footer другого отчёта не нужно переносить в новый.
- У `/topword` **нет заголовка, повторения искомого слова, строки «За всё время», шапки колонок и footer**. Не возвращать их при изменении Rich или HTML варианта.
- Основные сведения, текущий статус и ключевые числа видны сразу. В Rich основные секции могут быть открытыми `<details open>`, дополнительные — закрытыми `<details>`.
- Причина ограничения, результат модерации и кнопки решения не должны быть доступны только после раскрытия подробностей. Длинная цитата или вторичная статистика могут сворачиваться.
- Для списка полей использовать пары «название → значение». В Rich это компактная таблица без шапки «Параметр / Значение»; в HTML — строки с теми же полями.
- Для сравнения нескольких показателей использовать таблицу с короткими понятными заголовками колонок. Шапка нужна, если без неё неоднозначно значение чисел.
- Rich-таблицы следуют существующему оформлению `bordered striped`. Не выравнивать колонки пробелами и не рисовать таблицы символами псевдографики.
- Не собирать в одну широкую таблицу основную и всю дополнительную статистику. Для нового вывода больше четырёх основных колонок требует обоснования в PR и проверки читаемости на телефоне.

## 3. Текст и данные

- Основной язык — русский. Подписи короткие и предметные: «Сообщения», «Реакции», «Причина», «До». Не показывать raw enum, debug-структуры, JSON и названия внутренних jobs.
- В статистике переиспользовать [`StatsStrings`](../src/features/stats/strings.rs). Общие подписи других карточек держать в соответствующем модуле, не размножать варианты одного названия между renderer.
- Жирным выделять ключевые значения и короткие подписи. Не выделять весь абзац, каждую ячейку или всю цитату.
- Число сопровождается понятным смыслом или единицей. `/topword` считает **вхождения слова**, а не число сообщений с этим словом.
- `0` означает измеренный ноль. «Нет данных» или «недоступно» означает отсутствие сведений; не подставлять ноль вместо ошибки, неизвестного статуса или недоступного профиля.
- Неизвестное ограничение не показывать как «ограничений нет». Подтверждённую спам-метку отделять от оценки риска: `78/100` — оценка, а не доказательство и не вероятность, если модель не калибрована как вероятность.
- Причина пользователя, цитата сообщения, bio и пояснение модели остаются отдельными полями. Чужой текст не должен выглядеть как инструкция бота, подтверждённый статус или кнопка действия.
- Emoji допустимы как короткий маркер типа события или статуса. Не украшать ими каждую строку. Custom emoji брать из существующих bindings и давать текстовый или обычный emoji fallback.
- Пустой рейтинг отвечает одной короткой фразой «Нет данных», без пустой таблицы и списка фиктивных участников.

## 4. Имена, ссылки и источники

- Участника показывать кликабельным читаемым именем. При известном username использовать существующий helper с `https://t.me/<username>`; иначе — `tg://user?id=<id>`. Где нужен переход к сообщению автора, переиспользовать `user_or_message_link`.
- Отсутствие username не должно убирать имя или ломать карточку. Недоступный профиль не отменяет отправку уже собранной статистики.
- В обычных рейтингах не печатать числовой user ID рядом с каждым именем. В карточке для модератора ID допустим для однозначного выбора цели; это исключение не переносится в публичный топ.
- Ссылку на сообщение строить из проверенных `chat_id` и `message_id` через существующие helpers. Ссылка ведёт в тот чат и к тому сообщению, данные которого показаны в карточке.
- Для перехода к источнику использовать подписи «Сообщение», «Оригинал сообщения» или дату. Числовой ID допустим как дополнительная диагностика, но не заменяет рабочую ссылку.
- В ответах `/ask` ссылки на доказательства должны оставаться кликабельными после рендера. Внутренний маркер `message_425668` без преобразования в ссылку не считается ссылкой на источник.
- Не создавать ссылки для отсутствующих источников и не подставлять соседнюю ветку вместо нужной. Если источник недоступен, сообщить об этом текстом.
- Отключать лишние link preview штатным механизмом отправки. Карточка не должна разрастаться из-за предпросмотра каждой ссылки.

## 5. Даты и необязательные сведения

- Для новых и изменяемых дат использовать общий time API fork-а: `TimeContext`, `DateTimeToken`, `DateTimeFormat` и настроенный часовой пояс. Не добавлять самостоятельные преобразования UTC или фиксированные смещения.
- Относительное время в пределах одной карточки рассчитывается от одного захваченного `now`; при повторе доставки уже подготовленный результат не должен менять дату или смысл.
- Период отчёта должен быть однозначен. Не называть накопленные показатели «за сегодня». Исключение в оформлении `/topword`: дополнительную строку периода не печатать; семантика команды описана в её документации.
- Bio, тег, аватар и личный канал — необязательные сведения. Приватность Telegram или ошибка загрузки фото не должны лишать пользователя текстовой карточки.
- Аватары прикладывать через поддерживаемые typed Rich blocks/attachments. Не вставлять `<img>` и не показывать пользователю file ID, путь к кэшу или ошибку скачивания.
- Отсутствующие декоративные поля пропускать. Для важного отсутствующего статуса оставить понятную подпись «Нет данных».

## 6. Модерация и кнопки

- В начале карточки должно быть понятно, какое событие рассматривается и кто цель. В репорте отдельно обозначать цель и репортёра.
- Причину и доказательство показывать перед дополнительными сведениями профиля. Длинный исходный текст — цитатой, например `ExpandableBlockquote`, с явной подписью источника.
- Срок, область ограничения и результат действия показывать словами. Не заменять результат модерации общей надписью «Готово», если из неё непонятно, что изменилось.
- Навигационные кнопки и кнопки решения разделять по строкам. Подпись должна назвать действие: «Открыть сообщение», «Профиль», «Спам», «Не спам», «Верно: спамер», «Неверно: не спамер».
- После принятого решения обновлять исходную карточку и убирать неактуальные кнопки решения. Ошибка или неизвестный исход действия не должны выглядеть как подтверждённый успех.
- Карточка, предназначенная для лички администратора, остаётся в личке и при fallback. Не переносить её содержимое в публичный чат из-за ошибки оформления.

## 7. Рендер и доставка

- Rich и HTML получают одну typed-модель данных из service/repo. Renderer занимается представлением: SQL, получение профиля и расчёт бизнес-метрик выполняются до него. См. [`stats/document.rs`](../src/features/stats/document.rs).
- HTML-текст, имена, причины, bio и подписи ссылок экранировать через [`Html`](../src/telegram/html.rs). `raw_trusted` разрешён только для уже безопасно собранной внутренней разметки. Пользовательский текст и LLM output туда не передаются.
- Rich HTML компилировать штатным frontend fork-а либо строить сообщение из typed `InputRichMessage` blocks. `<h1>`, `<table>` и `<details>` относятся к Rich; нельзя отправлять их как обычный Telegram `ParseMode::Html`.
- Не добавлять собственный Telegram HTTP-клиент, wire-модели, CSS и обходы валидатора ради оформления. Использовать существующие [`render.rs`](../src/telegram/render.rs) и [`service_messages.rs`](../src/telegram/service_messages.rs).
- При сборке обычного HTML учитывать `SAFE_TEXT_LIMIT = 3900` и `TELEGRAM_TEXT_LIMIT = 4096`; application limit Rich — `32_768` символов. Считать длину штатными helpers, не байтами и не до экранирования.
- Длинные цитаты и превью обрезать существующим Unicode-safe helper с многоточием. Не обрезать всю готовую HTML-строку посередине тега или ссылки. При большом ответе использовать штатные подробности/файл.
- Fallback сохраняет имена, важные значения, статус, источник, назначение и reply-контекст. Он может упрощать оформление, но не молча терять текст или менять смысл.
- Ошибку отправки нужно обработать или передать вызывающему коду. При подтверждённом отклонении payload разрешён штатный fallback с исправлением формата; при неизвестном результате доставки нельзя отправлять вторую карточку и создавать возможный дубль.

## 8. Примеры структуры

Схемы ниже показывают порядок и плотность. Имена и числа условные; строки «Основное» и «Активность» в профиле обозначают секции, а не дополнительные заголовки таблиц.

### `/topword амудятел`

```text
1. Паша: 45 вхождений

2. Артём: 17 вхождений
```

В Rich это таблица без `<th>`, в HTML — список. Имена кликабельны, числа выделены. Добавлять перед ним «Топ по слову», слово запроса или период запрещено.

### `/userstatus`

```text
Паша

Основное [открыто]
Имя        Паша
Модерация  Без ограничений · предупреждений 0/3

Активность [открыто]
Сообщения  1240
Реакции    получено 318 · поставлено 96

Дополнительно [свёрнуто]
Первое сообщение   дата → ссылка
Последнее сообщение дата → ссылка
Частые слова        ...
```

Схема не требует выводить только эти поля: сохраняется общий набор данных профиля. Ручное выравнивание пробелами из схемы в Telegram не переносится.

### Репорт

```text
🚨 Новый репорт
↗ Оригинал сообщения
Цель: кликабельное имя · id=...
Репортёр: кликабельное имя · id=...
Сообщение: тип и время
Причина: текст репортёра

Цитата исходного сообщения [может сворачиваться]
Профиль / активность / антиспам: краткие сведения

[Открыть сообщение] [Профиль]
[Спам] [Не спам]
```

## 9. Приёмка изменений

Для изменения кода карточки в PR нужны пример итогового вывода и проверки затронутых сценариев:

- [ ] Выбран образец; нет дублирующих заголовков, пустых секций и декоративного шума.
- [ ] С телефона видны имя, важные числа/статус и смысл кнопок; таблица не требует читать множество вторичных колонок.
- [ ] Rich и HTML передают одинаковые данные; упрощение оформления явно не меняет значения.
- [ ] Проверены пустые данные, измеренный ноль и неизвестный статус.
- [ ] Имена, bio, причины и цитаты с `<`, `>`, `&`, кавычками и Unicode не ломают разметку и не теряют текст.
- [ ] Работают имя без username, недоступный аватар и настоящие ссылки на нужные сообщения.
- [ ] Проверены длинные поля, границы длины и затронутый fallback; неизвестный исход доставки не создаёт вторую карточку.
- [ ] Для модерации проверены кнопки до/после решения и сохранение адресата при fallback.

Проверки оформляются тестами затронутого renderer/доставки; для визуальной оценки нужен пример или снимок реально отрендеренной карточки. Документационная правка сама по себе не требует сборки и запуска бота.

Изменение этого стиля оформляется явно: в том же PR обновляется этот документ, приводится пример «до / после» и причина изменения. До такого изменения отклонение от контракта считается дефектом, а не новым образцом.
