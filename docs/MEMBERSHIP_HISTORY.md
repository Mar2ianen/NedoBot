# Членство и комментарии без вступления

Текущий Telegram ChatMemberLeft означает отсутствие в чате сейчас. Он не
различает бывшего участника и человека, который никогда не вступал. Ни
сообщения, ни first_seen_at, ни отсутствие сохранённого join event не доказывают
прошлое членство или отсутствие членства за всю жизнь аккаунта.

## Что проверено у других ботов

Проверка исходников 11 ноября 2026, без запуска чужого кода:

| Источник | Подход и граница |
|---|---|
| [Shieldy, 579cb1f](https://github.com/1inch/shieldy/blob/579cb1faf82ed6b31011f8198c73449eb70c262f/src/helpers/newcomers/index.ts) | Капча запускается по chat_member left → member; отдельно обрабатывается left_chat_member. Этот обработчик не даёт полной исторической классификации всех non-member. |
| [JoinCaptchaBot, 336ecb6](https://github.com/J-Rios/TLG_JoinCaptchaBot/blob/336ecb62c74292f260e3991190746b86c9830d42/src/tlgbotutils.py#L604) | Сравнивает реальное присутствие old/new, включая restricted.is_member. Поддерживает смену только is_member без смены строки status. |
| [Telegram Bot API](https://core.telegram.org/bots/api#chatmemberleft) | left описывает текущее состояние. Для chat_member updates бот должен быть администратором; подписка включается явно через allowed_updates. |

Вывод для NedoBot: сохранять положительные доказательства и не считать строку
restricted членством без проверки is_member. «Никогда не вступал» по Bot API
не восстанавливается ретроспективно. В NedoBot filter_chat_member уже входит
в dispatcher, который передаёт allowed-update hints polling listener.

## Представление

| Контекст | Основание |
|---|---|
| Состоит в чате | Последний доступный Telegram snapshot подтверждает присутствие. |
| Ранее состоял; сейчас не в чате | Сейчас отсутствует, сохранено положительное доказательство прежнего членства. Это не утверждение, что человек вышел добровольно. |
| Не в чате; история вступления неизвестна | Сейчас отсутствует, доказательства членства не сохранены. Не равнозначно «никогда не вступал». |
| Забанен в чате | Текущий banned/kicked. Сам по себе бан non-member не доказывает вступление. |
| Текущее членство неизвестно | Нет текущего состояния или оно противоречиво. |

Время последнего snapshot по-прежнему показывается в /userstatus. Cached status
не является новым live-подтверждением после ошибки Telegram API.

Оба формата /userstatus читают один MembershipContext из service DTO. Новая
строка появляется только в запрошенном отчёте. Приветствий, публичных справок
или уведомлений всем участникам нет; audience/fallback команды сохранены.

## Доказательства и scope

В своей БД, по ключу (chat_id, telegram_user_id), сохраняются
membership_first_confirmed_at и membership_last_confirmed_at. Это времена
наблюдения доказательства, не восстановленные точные даты входа/выхода.
Они сохраняются после left/banned snapshot и merge-ятся через MIN/MAX.

Источники: положительные getChatMember snapshots; old/new стороны настоящих
chat_member events; служебные new_chat_members/left_chat_member, где берётся
целевой пользователь, а не автор служебного сообщения. При restricted требуется
is_member=true. Обычный комментарий и legacy joined_at cache не дают доказательства.

Additive migration 20261111100000 переносит только такие сохранённые факты.
Неизвестные и malformed данные остаются неизвестными. Raw events не изменяются,
чужой chat не подтверждает членство в текущем, новую публичную MCP projection
или grants migration не добавляет. Права read-only роли не расширяются.

Новые события используют ChatMemberKind::is_present(), включая переходы
restricted(false) ↔ restricted(true). Строго более старый snapshot не заменяет
новое текущее состояние; историческое положительное наблюдение при этом не
теряется. Отдельный snapshot не создаёт выдуманное событие вступления.

## Антиспам и эксплуатация

Captcha eligibility различает историю через этот же helper, но бывшее членство
не становится whitelist, spam score или доказательством бана. Пороги,
классификатор, условия наличия своего комментария и ephemeral-only доставка
сохранены. Неизвестная история сама по себе не вызывает капчу.

Для rollback нужен binary, знающий additive migration: старый 3e5434b отклонит
неизвестную applied SQLx migration. Совместимый rollback source — migration-only
3af0d9223b4a0d2a61ded2c309b6329f99532cff, с прежним runtime поведением и тем же
checksum migration. Новый код и compatibility build должны проверяться против
одной неизменённой версии SQL. Миграцию после применения не переписывать,
наблюдения при rollback не удалять.
