# Антиспам без постоянного добавления фраз

Это предложение следующего этапа, а не описание включённого автообучения.
Сейчас есть нормализация гомоглифов, конфигурируемые lexical campaign rules,
локальный линейный классификатор, embedding head/similarity и журнал
`spam_label_events`. Campaign rules включены через `include_str!`: добавление
синонимов требует rebuild и не решает перефразирование.

На 9 ноября 2026 в двух production БД есть 196 ручных событий `spam`
(130 NedoNews + 66 PVO) и 21 ручное `not_spam` (19 + 2). Это числа событий,
не размер независимого обучающего корпуса: нужны dedup и последнее решение.
Тысячи `system/not_spam` нельзя автоматически считать проверенными людьми
отрицательными примерами. Предыдущие ответы модели нельзя использовать как
собственное подтверждение правильности новой модели.

## Предлагаемый порядок

1. **Решение модератора становится обучающим примером.** Собирать в одной
   транзакции последнюю ручную метку, конкретное сообщение/первые сообщения,
   источник решения и время. Ручной ban без сообщения или проверяемой причины
   помечать кандидатом, а не автоматически размечать всю историю автора.
   `/notspam` и отмена решения должны отзывать пример и основанные на нём
   template-сигналы. Полные private сообщения и conversation memory в корпус
   группового антиспама не добавлять.
2. **Похожие кампании подхватываются из размеченного корпуса.** Хранить
   нормализованный текст, char n-grams/MinHash fingerprint, embedding и ссылку
   на подтверждённый пример. При новой метке обновлять индекс без изменения
   Rust-кода. Поиск учитывать и spam, и проверенные normal соседи; ответ
   «похож на такое-то подтверждённое сообщение» сохранять в evidence.
   Один шаблон с одной спорной меткой не должен становиться безусловным баном.
3. **Переобучать дешёвую модель по расписанию.** Начать с word 1–2 + char 3–5
   TF-IDF и логистической регрессии. Символьные признаки покрывают опечатки,
   разбивки и похожие написания, комбинации слов — новые формулировки. Уже
   подключённый linear model backend позволяет сохранить локальный inference.
   Порог калибровать отдельно для review и enforcement; явно измерять долю
   вызовов LLM. Сначала сравнивать candidate со старой моделью без действий.
4. **Просить разметку пограничных сообщений.** В существующую review-очередь
   отправлять ограниченное число разногласий lexical/linear/similarity,
   новых кластеров и пропущенных сообщений забаненных авторов. Человек
   подтверждает пример кнопкой, а не придумывает regex и коэффициенты.
5. **Выпускать проверенный model artifact.** Делить train/validation/test по
   времени, автору и кластеру кампании; держать отдельные отчёты по инстансам.
   Иначе копии одного объявления создадут ложную точность. Сравнивать recall
   на новых ручных банах, precision, false positives на проверенных normal,
   нагрузку review и LLM calls/1000 сообщений. Хранить версию корпуса, метрики,
   checksum модели и прошлую модель для rollback. При недостатке normal
   примеров новый порог enforcement не повышать на основании одной оценки.

## Обработка сообщения

`нормализация → подтверждённые шаблоны + local linear → pgvector similarity
для сомнительных случаев → ограниченная review/LLM очередь`.

Для заведомо обычных сообщений LLM не нужен. Совпадение с кампанией сохраняет
проверяемые основания; реальные действия по-прежнему проверяют свежесть,
scope, разрешённый чат, актуальный `not_spam` и обычную moderation policy.
Снятие метки или ошибка индекса не должны приводить к новому бану.
Между инстансами можно использовать уже согласованную spam reputation;
перенос текстового корпуса требует отдельного явного решения.

## Нужен ли OpenSearch/Elasticsearch

Первую версию стоит сделать на имеющемся PostgreSQL: `pg_trgm`/GIN для
лексического поиска и существующий pgvector для embedding similarity.
Данные уже там, объём ручной разметки невелик, не появляется второй источник
правды и отдельная синхронизация удалений. OpenSearch имеет смысл после
измеренного недостатка latency/масштаба PostgreSQL или потребности в сложном
BM25/hybrid search. Он ускоряет поиск похожих примеров, но сам не заменяет
разметку, калибровку и проверку false positives.

Ближайший полезный PR: единый exporter последней ручной разметки, воспроизводимый
replay-report и обновляемый индекс подтверждённых шаблонов. Следующий —
плановое обучение и shadow-проверка новой linear модели. Новые списки фраз
добавлять только для действительно новых структурных признаков.

Основания для выбранных механизмов: [pg_trgm: similarity и GIN/GiST indexes](https://www.postgresql.org/docs/16/pgtrgm.html),
[pgvector: поиск ближайших соседей](https://github.com/pgvector/pgvector),
[scikit-learn: text/character n-grams и TF-IDF](https://scikit-learn.org/stable/modules/feature_extraction.html#text-feature-extraction).
Выбор первого шага на PostgreSQL — инженерное предложение для текущей архитектуры,
его latency и качество надо измерить replay-отчётом.
