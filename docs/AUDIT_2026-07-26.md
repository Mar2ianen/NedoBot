# Приоритетные исправления

## P0 — закрыть до следующего публичного расширения MCP

### P0.1. Public MCP может опубликовать сообщение не из discussion chat

**Где:** `migrations/20260717180000_mcp_public_views.sql:5-15`.

```sql
from public.telegram_messages
where chat_id = -1001932061163
   or source_channel_id = -1001575496091;
```

**Проблема:** `save_telegram_message` сохраняет сообщения не только из discussion chat. Если пост исходного канала переслан боту в личку или иной чат, строка может иметь `source_channel_id`, но другой `chat_id`. Такое сообщение попадёт в `mcp_public.telegram_messages`, хотя README и TECHNICAL обещают отсутствие private chats.

**Исправление:** новая additive migration с `CREATE OR REPLACE VIEW`, где `mcp_public.telegram_messages` ограничивается `chat_id = discussion_chat_id`. Аналогично проверить все public views с predicate вида `discussion_chat_id = ... OR source_channel_id = ...`.

**После миграции:** проверить уже опубликенные данные запросом по `chat_id <> -1001932061163 and source_channel_id = -1001575496091`; решить, нужно ли удалить эти строки из исходной таблицы или достаточно исключить их из projection.

**Тест:** integration test против PostgreSQL: сообщение из private chat с `source_channel_id` не видно через MCP view.

## P1 — исправить скрытые runtime-ошибки и потерю работы

### P1.1. Embedding jobs создаются при выключенном worker-е

**Где:**

- `src/db/telegram.rs:200-203`;
- `src/features/chat_retrieval.rs:340-376`;
- `src/main.rs:116-139`.

**Проблема:** каждое новое или отредактированное сообщение вызывает `enqueue_message_embedding`, но worker запускается только при `CHAT_RETRIEVAL_EMBEDDINGS_ENABLED=true`. При дефолтном `false` база бесконечно копит `pending` jobs.

**Последствия:** лишний рост таблицы и индексов; непредсказуемо большой backlog при последующем включении фичи.

**Исправление:** не ставить job в очередь, когда ingestion выключен. Предпочтительный путь — передавать policy/config до enqueue; альтернативно — отдельный ingestion service, который вызывается только при включённой feature.

**Тесты:**

1. disabled mode не вставляет строку в `telegram_message_embeddings`;
2. enabled mode создаёт ровно одну job;
3. edit переоткрывает существующую ready-job только при enabled mode.

### P1.2. First-message spam скрыто зависит от avatar и RAG конфигурации

**Где:**

- `src/main.rs:66,311-326`;
- `src/features/first_message_spam.rs:49,279-296`;
- `src/config.rs:334-356`.

**Проблема:** first-message spam worker стартует всегда и вызывает:

- `embed_text` через RAG embedding service;
- Cerebras с `provider_override: Some("cerebras")`;
- `avatar_classifier_model` как модель текстового spam-классификатора.

При `AVATAR_CLASSIFIER_ENABLED=false` startup уже не требует `CEREBRAS_API_KEY`, но spam worker всё равно вызывает Cerebras. При `RAG_ENABLED=false` startup не проверяет embedding endpoint, но worker всё равно вызывает embeddings. Результат — бот стартует успешно, а новые jobs уходят в retry/fail.

**Исправление:** добавить независимую конфигурацию:

```env
FIRST_MESSAGE_SPAM_ENABLED=true
FIRST_MESSAGE_SPAM_PROVIDER=cerebras
FIRST_MESSAGE_SPAM_MODEL=...
```

При включении валидировать provider secret/model и обязательную embedding-зависимость. Если feature выключена — не стартовать worker и не создавать jobs.

### P1.3. Avatar signal может пересечь `high`, но review-карточка не создаётся

**Где:**

- `src/features/avatar_analysis/service.rs:181-241`;
- `src/main.rs:206-224`.

**Проблема:** avatar worker обновляет `risk_score` и `risk_level`, но не вызывает `create_high_risk_review`. Review создаётся только после profile audit и после first-message spam analysis.

**Исправление:** после успешного `apply_avatar_risk_signal` вызвать idempotent `create_high_risk_review` и `send_review`; лучше вынести проверку перехода в `high` в один domain hook, общий для всех источников риска.

**Тест:** avatar signal повышает low/medium profile до high и создаёт один `spam_review_requests`; повторная обработка не создаёт дубль.

### P1.4. Первый комментарий остаётся `pending` после live failure

**Где:**

- `src/features/first_comment/pipeline.rs:63-301`;
- `src/features/first_comment/repo.rs`;
- `src/bin/retry_pending_comments.rs`.

**Проблема:** live pipeline создаёт `post_comment_jobs` до LLM/send. При ошибке job не получает error/status. Dedup не позволит повторно запустить этот пост через incoming update; восстановление возможно только ручным `retry_pending_comments`.

**Исправление в два этапа:**

1. минимально: добавить `mark_post_comment_failed` и сохранять безопасный error kind в live pipeline;
2. правильно: сделать постоянный worker с claim/lease/retry, аналогичный history/avatar/spam jobs.

Не записывать в БД и логи необработанные API error bodies или URL с токенами.

## P2 — надёжность, конфигурация и защита публичного endpoint

### P2.1. Public MCP нужен rate limit против спама

**Где:** `src/bin/nedonews_mcp_http.rs:304-346`, `deploy/vpn-nginx/nginx.conf:70-80`.

Endpoint намеренно публичный. Ограничение должно защищать не от легитимного исследования, а от flood, crawler abuse и дорогих запросов.

**Решение:** добавить nginx `limit_req` и `limit_conn` с достаточно большим burst. Например, стартовая политика:

- 30 запросов/минуту/IP sustained;
- burst 60 без delay либо с мягким delay;
- 4 одновременных соединения/IP;
- отдельный более строгий лимит для тяжёлых `db.search_text` и `db.aggregate`, если понадобится по логам.

Не использовать CORS как защиту: запрос без `Origin` сейчас разрешён, а CORS не блокирует server-to-server clients.

### P2.2. Невалидный `.env` тихо превращается в default

**Где:** `src/config.rs:588-635`.

`env_bool`, `env_i64`, `env_u32`, `env_u64`, `env_usize`, `env_f32`, `env_f64` тихо возвращают default при невалидном заданном значении. Например, `VOICE_AUTO_TRANSCRIBE=TRUE` становится `false`, а ошибочный лимит меняется на default.

**Исправление:** `Config::from_env()` должен возвращать `anyhow::Result<Config>`. Если env var существует, но не парсится — startup fail-fast с именем переменной и допустимым форматом. Для bool явно поддержать только документированные `true`/`false` либо также `1`/`0`.

### P2.3. Profile refresh создаёт неограниченную очередь `tokio::spawn`

**Где:** `src/main.rs:166-243`.

Semaphore ограничивает сетевые операции, но задача создаётся до получения permit. При message flood тысячи futures будут ждать permit в памяти.

**Исправление:** bounded `tokio::sync::mpsc` queue и фиксированное количество workers. При заполнении очереди — skip/debounce, лог/метрика, но не бесконечное накопление task-ов.

### P2.4. Feature flags не описывают зависимости

**Где:** `src/config.rs`, `src/features/chat_retrieval.rs:81-132`.

`CHAT_RETRIEVAL_SHADOW_ENABLED` вызывает embedding requests без обязательной проверки embedding config. `CHAT_RETRIEVAL_EVIDENCE_ENABLED` не требует shadow mode. Аналогичная проблема есть у first-message spam.

**Исправление:** формализовать validation rules:

```text
shadow retrieval => embedding ingestion + valid embedding endpoint
chat evidence => shadow retrieval
first-message spam => provider/model/secret + embeddings
voice cleanup provider => provider/model/secret
```

При несовместимой конфигурации — fail-fast, а не скрытая деградация в runtime.

### P2.5. Voice DB не хранит реальный cleanup provider/model

**Где:** `src/features/voice/pipeline.rs:131-142`, `src/features/voice/repo.rs:98-125`.

Колонки существуют, но `save_voice_result` не пишет фактический provider/model. Нельзя расследовать fallback cleanup.

**Исправление:** заменить возвращаемый тип cleanup на:

```rust
struct CleanupResult {
    provider: String,
    model: String,
    transcript: CleanTranscript,
}
```

и сохранять provider/model в одной транзакции с cleaned result.

# Архитектурный долг

## A1. HTML и Rich statistics дублируют domain queries

**Где:** `src/features/stats/report.rs` — 2811 строк.

Примеры повторов:

- summary/attraction queries: `1165-1278` и `2072-2212`;
- top-users queries: `1324-1367` и `2214-2312`;
- похожая логика top bot comments в rich и HTML путях.

**Проблема:** форматы отчёта стали отдельными продуктами. Новая метрика или исправление может попасть только в один renderer.

**Целевая структура:**

```text
features/stats/
├── repo.rs       — SQL и typed DTO
├── service.rs    — period, aggregation, profile refresh policy
├── render_html.rs
├── render_rich.rs
└── types.rs
```

`render_html` и `render_rich` не должны знать SQL. Оба получают одну модель `ChatStatsReportData`.

## A2. Два самописных MCP сервера повторяют transport и read-model логику

**Где:**

- internal stdio MCP: `src/features/ask/chat_db_mcp.rs`;
- public HTTP MCP: `src/bin/nedonews_mcp_http.rs`.

Они дублируют readonly pool setup, protocol structs, tool schemas, pagination, DB projections, лимиты и части sanitization.

### A2.1. Ближайшее значимое обновление MCP protocol нужно включить в одну миграцию

Сейчас версии уже расходятся:

- internal stdio MCP объявляет `protocolVersion: "2024-11-05"` в `src/features/ask/chat_db_mcp.rs`;
- public Streamable HTTP MCP объявляет `protocolVersion: "2025-11-25"` в `src/bin/nedonews_mcp_http.rs`.

Ожидаемое значимое обновление MCP protocol не следует накладывать поверх двух самописных реализаций по отдельности. Это создаст третью несовместимую ветку protocol behavior, lifecycle и schema handling.

**Решение:** сделать обновление protocol version частью одного перехода на `rmcp`:

1. выбрать релиз `rmcp`, поддерживающий целевую актуальную версию MCP;
2. поднять stdio и Streamable HTTP adapters на одном protocol implementation;
3. сохранить единые tool names/input-output schemas, public scope и read-only guarantees;
4. добавить compatibility tests с целевыми MCP clients для `initialize`, `tools/list`, `tools/call` и error responses;
5. зафиксировать поддерживаемую версию в `AGENTS.md`, TECHNICAL и deploy smoke checklist.

До этой миграции не добавлять новые ручные JSON-RPC structs, protocol versions или lifecycle code в существующие MCP binaries.

### Направление: перейти на `rmcp`

Использовать `rmcp` как единый protocol/transport layer для обоих сценариев:

- stdio transport для `/ask`;
- Streamable HTTP transport для public MCP;
- единое описание tools и JSON Schema;
- нормальный lifecycle, protocol compatibility и error formatting без ручного JSON-RPC.

**Важно:** `rmcp` не должен получить прямой доступ к произвольному SQL. Его tools должны вызывать отдельный application/read-model слой.

Целевая граница:

```text
features/chat_read_api/
├── service.rs       — use-cases: search, context, profiles, notes
├── queries.rs       — typed SQL queries и лимиты
├── public.rs        — public DTO/projections и redaction
├── agent.rs         — richer agent-only DTO/projections
└── policy.rs        — scope и access decisions

telegram/ask adapter -> rmcp stdio server -> chat_read_api::agent
public MCP adapter   -> rmcp HTTP server  -> chat_read_api::public
```

Это не означает объединять permissions. Public и agent-only DTO должны остаться разными, а public scope — явно более узким.

## A3. Business orchestration разрослась в `main.rs` и `command_handler.rs`

**Где:**

- `spawn_message_author_profile_refresh` в `src/main.rs` одновременно делает refresh, new-user audit, spam job enqueue, review и avatar enqueue;
- `handle_ask_command` в `src/telegram/command_handler.rs` совмещает authorization, audit, progress-message, agent lifecycle, rendering и fallback.

**Направление:**

- `ProfileEnrichmentService::enqueue_for_message`;
- `AskService::answer_and_audit`;
- `AskProgressReporter` как Telegram adapter;
- `main.rs` — только dispatcher/wiring/worker startup;
- `command_handler.rs` — parse command, authorize, invoke service, send result.

## A4. Job lifecycle реализован разными несовместимыми способами

Сейчас есть разные реализации retry/lease/status:

- post history: status `pending/retry/processing/ready/ignored/failed`;
- avatar: `pending/retry_wait/processing/succeeded/failed`;
- first-message spam: похожая, но отдельная;
- embeddings: отдельные query fragments и другая backoff-policy;
- post comments: ручной bin вместо worker.

**Первый шаг без внешней зависимости:** общий `jobs` module с:

- `RetrySchedule`;
- константами lease/poll interval;
- typed `ErrorKind`;
- helper-ами для safe finalization;
- едиными метриками queue age, attempts, failed count.

Не стоит немедленно абстрагировать SQL claim целиком: таблицы разные. Достаточно унифицировать policy и инварианты.

## A5. Монолитный `Config` и дублированные test fixtures

`Config` содержит около 115 полей. Полные fixtures дублируются минимум в четырёх тестовых модулях.

**Направление:** nested configs и тестовый builder:

```rust
Config::test_defaults()
    .with_voice(...)
    .with_search(...)
    .with_ask(...)
```

В production `Config` можно сохранить как единый root, но разделить на `TelegramConfig`, `LlmConfig`, `RagConfig`, `SearchConfig`, `AskConfig`, `VoiceConfig`, `SpamConfig`.

# LLM provider profiles и Alibaba Model Studio

## Проблема текущего router-а

Сейчас список провайдеров зашит в нескольких местах:

- `Config` содержит отдельные `GROQ_*`, `CEREBRAS_*`, `OPENROUTER_*` поля;
- `normalize_llm_provider` допускает фиксированный enum строк;
- `validate_llm_provider_secret` и `validate_llm_provider_model` знают каждый бренд;
- `model_for_provider` дублирует выбор model;
- `generate_once` сопоставляет бренд с base URL и ключом.

В результате добавление Alibaba/Qwen или любого следующего OpenAI-compatible провайдера требует менять router, config, validation, fixtures, `.env.example` и документацию. Это именно тот тип provider hardcode, от которого стоит уйти.

## Целевая модель: небольшое число protocol drivers, произвольные profiles

Оставить в Rust только реальные несовместимые форматы:

```text
Driver
├── gemini                 — Google GenerateContent API
├── ollama                 — Ollama /api/chat
└── openai_compatible      — `async-openai` Chat Completions API
```

`async-openai = 0.41` уже есть в `Cargo.toml`, но сейчас не используется; вместо него проект держит собственный `src/llm/openai_compat.rs` на `reqwest`. Это нужно заменить, а не строить ещё один generic HTTP client.

В доступной версии `async-openai` есть `OpenAIConfig::with_api_base`, `with_api_key` и `with_header`, то есть crate покрывает custom endpoint, ключ и допустимые provider-specific static headers.

Groq, Cerebras, OpenRouter, OpenAI-compatible custom endpoint и Alibaba Model Studio должны быть **profiles** одного `openai_compatible` driver, а не вариантами enum в коде.

Пример коммитящегося шаблона `config/llm_profiles.toml.example`:

```toml
[providers.groq]
driver = "openai_compatible"
base_url = "https://api.groq.com/openai/v1"
api_key_env = "GROQ_API_KEY"
default_model = ""
structured_output = "json_schema"

[providers.cerebras]
driver = "openai_compatible"
base_url = "https://api.cerebras.ai/v1"
api_key_env = "CEREBRAS_API_KEY"
default_model = ""
structured_output = "json_schema"

[providers.openrouter]
driver = "openai_compatible"
base_url = "https://openrouter.ai/api/v1"
api_key_env = "OPENROUTER_API_KEY"
default_model = ""
structured_output = "json_schema"

[providers.alibaba]
driver = "openai_compatible"
# Выбрать endpoint нужного Alibaba Model Studio региона по актуальной официальной документации.
# Не хардкодить China/International endpoint в Rust.
base_url = "https://dashscope-intl.aliyuncs.com/compatible-mode/v1"
api_key_env = "DASHSCOPE_API_KEY"
default_model = "qwen-plus"
structured_output = "json_schema"
```

Alibaba Cloud Model Studio официально документирует OpenAI-compatible Chat Completion interface. DashScope endpoint зависит от региона аккаунта; production config обязан явно задавать `base_url`, а ключ хранится только в переменной окружения, указанной через `api_key_env`.

Роли используют имена profiles, а не типы транспорта:

```env
LLM_PROVIDER=gemini_comment
MEMORY_LLM_PROVIDER=ollama_memory
ASK_LLM_PROVIDER=alibaba
VOICE_CLEANUP_PROVIDER=groq
FIRST_MESSAGE_SPAM_PROVIDER=cerebras
```

Для Gemini fallback chain лучше хранить также как routing policy, а не в `match`:

```toml
[routes.first_comment]
providers = ["gemini_comment", "gemini_flash", "gemini_lite", "ollama_memory"]

[routes.memory]
providers = ["ollama_memory"]
```

## Обязательные capability поля profile

Не определять возможности по имени модели, как сейчас в `supports_images`. Profile должен явно сообщать:

```toml
supports_images = false
structured_output = "json_schema" # json_schema | json_object | prompt_only
request_timeout_sec = 45
```

Это позволит корректно различать:

- OpenAI-compatible providers с полноценной JSON Schema;
- providers, где нужен `json_object` fallback;
- providers, где остаётся только prompt contract;
- image-capable и text-only models.

Provider-specific static headers, если они действительно нужны, можно хранить allowlisted map в profile. Секретные headers должны ссылаться на env var, а не попадать в TOML или логи.

## Порядок миграции без breaking change

1. Добавить `LlmProviderProfile` и loader profiles, ничего не удаляя.
2. Перенести существующие Groq/Cerebras/OpenRouter/OpenAI-compatible настройки в встроенные compatibility profiles.
3. Переключить `generate_once` на `async_openai::Client<OpenAIConfig>`, сконфигурированный из profile через `with_api_base` и `with_api_key`; model/secret validation и capability checks перевести на profile.
4. Удалить самописный `OpenAiCompatClient` после эквивалентных request-shape tests, затем добавить Alibaba profile и smoke test без реального API key.
5. Перевести `.env.example` на profile names.
6. После production migration удалить брендовые поля и `normalize_llm_provider` варианты для OpenAI-compatible брендов.

Gemini и Ollama не нужно насильно прогонять через OpenAI-compatible API: отдельные native drivers дают доступ к их нужным возможностям и сохраняют корректный формат запросов.

# Зрелые crate-ы вместо самописной инфраструктуры

Новые зависимости стоит добавлять только если они заменяют заметный объём protocol/infra кода. Бизнес-правила, SQL projections и Telegram-specific rendering не нужно выносить в crates ради самого выноса.

| Область | Сейчас | Кандидат | Практическое решение |
| --- | --- | --- | --- |
| OpenAI-compatible LLM client | самописный `OpenAiCompatClient` на `reqwest`; `async-openai` уже импортирован, но не используется | `async-openai` | Приоритетно для Groq/Cerebras/OpenRouter/Alibaba/custom endpoint-ов: использовать `OpenAIConfig::with_api_base` и profiles, затем удалить собственный client. |
| MCP protocol и transports | два самописных JSON-RPC/MCP сервера | `rmcp` | Приоритетно. Перевести stdio и public Streamable HTTP на `rmcp`, но оставить собственный allowlisted read-model слой. |
| HTTP rate limit | отсутствует | `tower-governor` / `governor`, либо nginx `limit_req` | Для public endpoint начать с nginx — он уже в deploy и лучше гасит flood до Rust. `tower-governor` добавить, если нужны разные limits для MCP tools или in-process telemetry. |
| HTTP middleware | часть hand-rolled в Axum/Nginx | `tower-http` | Добавить `TraceLayer`, request ID, timeout/body-limit layers для public MCP. Не использовать для логирования sensitive headers/body. |
| Config parsing | custom `env_*` с silent fallback | `figment` или `config` + `serde` + `dotenvy` | `figment` подходит для объединения `.env` и env vars, но обязательно оставить strict deserialize/startup validation. Если migration рискованна, сначала сделать собственные strict parsers — это маленький и надёжный fix без crate. |
| Retry только для transient external calls | разрозненный ручной код | `backon` | Использовать для HTTP request-level retry с jitter, только где операция idempotent. DB job retry/state transitions оставить явными в коде. |
| Полноценный Postgres job framework | custom SQL job queues | `apalis` (оценить отдельно) | Не мигрировать срочно. Текущий подход с `FOR UPDATE SKIP LOCKED` подходит. Сначала унифицировать собственные policies; затем сравнить Apalis по maintenance и migration cost. |
| Markdown parsing | custom rich markdown validator | `pulldown-cmark` | Рассмотреть только для parsing/AST. Telegram Rich Markdown и URL allowlist всё равно требуют собственного policy layer; не заменять валидатор «сырым markdown renderer-ом». |
| Unicode text segmentation | много `.chars().take(...)` | `unicode-segmentation` | Полезен при будущих строгих UI limits и truncation по grapheme clusters. Не является срочным security fix. |
| URL parsing | используется `reqwest::Url` | `url` как direct dependency при необходимости | Не обязательно: текущий `reqwest::Url` уже корректен. Добавлять direct dependency только если URL policy станет общим модулем. |

## Не стоит добавлять сейчас

- полноценный ORM поверх SQLx;
- generic repository framework;
- message broker только ради нескольких PostgreSQL job queues;
- отдельный workflow engine;
- HTML sanitizer как замену текущему typed HTML builder.

У проекта много предметных SQL запросов и строгих public projections: SQLx + typed DTO остаётся более прозрачным вариантом.
